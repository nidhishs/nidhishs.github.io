You have a model and some serving constraints to meet. How many GPUs does it take to serve? You can answer that on a napkin, using numbers you already know. It comes down to two questions.

<em>Does it fit?</em> The weights and the KV cache have to live in GPU memory. This is the easy one, and where most people stop.

<em>Can it keep up?</em> The GPUs have to push tokens fast enough to hit your rate without missing the latency target. This is where the GPU count usually comes from.

## The Answer in One Line

Call the three bills memory, prefill, and decode. The model has to fit, and it has to keep up:

$$
G = \max\big(G_\text{fit},\ G_\text{prefill} + G_\text{decode}\big)
$$

| Bill | Question | Bottleneck |
|:--|:--|:--|
| $G_\text{fit}$ | Do weights and KV cache fit? | GPU memory capacity |
| $G_\text{prefill}$ | Can we process prompts fast enough? | FLOPs |
| $G_\text{decode}$ | Can we generate tokens fast enough? | HBM bandwidth |

For the running example below, Qwen3-8B on H200s at 2 req/s with 4K input and 1K output, the bills come out to about 0.7 cards to fit, 0.3 for prefill, and 0.5 for decode. That rounds to one H200. Push the same workload to 20 req/s and it becomes about eight.

## What You Need

You need three groups of inputs:

- **Model:** total parameters $P$, active parameters $P_a$, precision, and attention architecture.
- **Hardware:** memory per GPU $M_\text{gpu}$, bandwidth $\text{BW}$, and peak compute $F$.
- **Demand:** request rate $R$, input length $L_\text{in}$, output length $L_\text{out}$, and TPOT target.

$P_a$ is equal to $P$ for a dense model. For an MoE, $P$ is the total resident parameter count, while $P_a$ is the active parameter count per token. Precision sets bytes per parameter: 2 for bf16, which we use throughout, or 1 for fp8.

For hardware, an H200 has 141 GB of HBM, 4.8 TB/s of bandwidth, and about 990 dense bf16 TFLOPS :content-cite{n="1"}. The datasheet's larger bf16 number assumes sparsity; for dense weights, use half.

TPOT means time per output token. In the examples below, the decode SLO is 50 ms/token. If the model writes 1,000 output tokens, that is a 50 second decode window.

The running anchor is the case I'll carry through the memory, prefill, and decode bills, before varying the parameters at the end:

$$
R = 2\text{ req/s}, \quad L_\text{in}=4{,}000, \quad L_\text{out}=1{,}000, \quad t=50\text{ ms}.
$$

## Two Questions, Three Resources

The two questions turn into three resource bills. <em>Does it fit?</em> is about capacity: the weights and the live KV cache have to sit in GPU memory at the same time. <em>Can it keep up?</em> is about throughput, but generation does not have a single bottleneck from start to finish.

Prefill reads the prompt all at once, runs large matrix multiplies, and is compute-bound :content-cite{n="8"}. Decode writes one token at a time. Serving engines batch many streams together, but each decode step still streams weights and KV cache from HBM, so decode is bandwidth-bound :content-cite{n="10"}. That split is why the final count has one memory bill and two throughput bills.

## Step 1: Does It Fit?

Capacity has two parts: the weights, which are fixed, and the KV cache, which grows with the number of live tokens. Start with the fixed part.

### The Weights

The weights are the easy part. Multiply parameters by bytes per parameter:

$$
M_\text{weights} = P \times b
$$

Here, $b$ is bytes per parameter. Qwen3-8B is 16 GB at bf16, and the 30B-A3B MoE is 60 GB. That MoE number uses the <em>total</em> parameter count, not the 3B active count, because every expert has to be resident even though a given token routes through only a few.

### The KV Cache

The KV cache is the term you cannot read off the model's parameter count. During generation, each token's keys and values are stored so later tokens can attend to them. The bytes per token depend on the attention design: number of layers, KV heads, head dimension, and precision.

For standard grouped-query attention :content-cite{n="2"}, the expression includes both keys and values. The per-token cache is:

$$
M_\text{kv/tok} = 2 \times n_\text{layers} \times n_\text{kv heads} \times d_\text{head} \times b
$$

The leading 2 is for keys and values. So yes, the KV-per-token number can be calculated, but you need architectural details: layer count, number of KV heads, head dimension, and dtype. If the model uses a hybrid or compressed attention scheme, use its actual cache layout instead of this standard-GQA formula.

Qwen3's dense line is a clean example: 8 KV heads and head dim 128 across sizes. That is 4 KB per layer at bf16 :content-cite{n="6"}. The cache is then 4 KB times the layer count. The 8B has 36 layers, so 144 KB per token; the 0.6B has 28 layers, so 112 KB. Despite a more than 10x parameter gap, their KV caches are in the same ballpark.

<em>However</em>, nobody keeps layer counts in their head, so a rule of thumb helps. For standard dense GQA at bf16, the table below gives a ceiling; use it for any model whose attention you have not checked.

| Model size | KV cache per token |
|:----------:|:------------------:|
| 0.6B       | ~112 KB            |
| 8B         | ~144 KB            |
| 32B        | ~256 KB            |
| 72B        | ~320 KB            |

::content-collapsible{title="What if my model isn't standard GQA?"}
For most modern architectures, the table still works as a conservative ceiling. Newer attention variants usually shrink the KV cache. The savings vary a lot, though: the gap swings more than an order of magnitude depending on the trick.

Qwen3.5's Gated DeltaNet hybrid :content-cite{n="3"} runs full attention on just one in four layers. The other three use linear attention, whose state does not grow with the sequence. So the model lands around a quarter of the standard-GQA figure.

DeepSeek's multi-head latent attention takes the other route: it keeps every layer, but compresses each layer's per-head keys and values into a single shared latent vector, cutting per-token KV storage by over 90% :content-cite{n="3"}. One cuts how many layers cache, the other how much each layer caches.
::

The table is per token; multiply it by average sequence length and requests in flight to get total KV bytes in memory :content-cite{n="4"}:

$$
M_\text{kv} = M_\text{kv/tok} \times \text{seq len} \times \text{concurrency}
$$

Concurrency comes from Little's Law: requests in flight equal rate times latency. For generation, napkin latency is output tokens times TPOT; add prefill and queueing if those are meaningful fractions of your SLO:

$$
\text{latency} \approx L_\text{out} \times t
$$

For the anchor, TPOT is 50 ms and $L_\text{out}=1{,}000$, so each request occupies the system for about 50 seconds. At 2 req/s, Little's Law gives 100 requests in flight. The average sequence length during decode is:

$$
\bar n = L_\text{in} + L_\text{out}/2 = 4{,}000 + 1{,}000/2 = 4{,}500.
$$

Qwen3-8B has 16 GB of bf16 weights and a standard-GQA cache of 144 KB/token, so:

$$
M_\text{kv} \approx 144\text{ KB} \times 4{,}500 \times 100 \approx 65\text{ GB}.
$$

The memory you need to fit is weights plus KV cache, with about 15% extra for CUDA context, fragmentation, and activation buffers:

$$
M_\text{fit} = (M_\text{weights} + M_\text{kv}) \times 1.15
$$

$$
G_\text{fit} = M_\text{fit} \,/\, M_\text{gpu}
$$

Dividing by 141 GB of H200 memory gives the fit bill:

$$
G_\text{fit} \approx \frac{(16\text{ GB} + 65\text{ GB}) \times 1.15}{141\text{ GB}} \approx 0.7
$$

  <strong class="text-foreground font-medium">Takeaway:</strong>
  Fitting the model is weights plus live KV cache. KV cache scales with traffic shape and attention design, not just parameter count.
</aside>

## Step 2a: Prefill Is a Compute Bill

Prefill reads the prompt. Every input token is processed together in one large matrix-multiply batch, so compute units stay saturated and the phase is compute-bound :content-cite{n="8"}. That makes the GPU bill a FLOP budget: demand is rate times tokens-per-request times FLOPs-per-token, and supply is MFU times peak compute $F$, with MFU $\approx 0.5$ :content-cite{n="8"}.

The per-token cost $C_\text{in}$ has two terms. The weight term ($2P_a$) is one multiply-add per active parameter. The attention term ($4\,n_\text{layers}\,d_\text{hidden}\,L_\text{in}$) comes from scoring each query against every prior key and summing weighted values across all layers:

$$
C_\text{in} = 2P_a + 4\,n_\text{layers}\,d_\text{hidden}\,L_\text{in}
$$

$$
G_\text{prefill} = \frac{R \times L_\text{in} \times C_\text{in}}{\text{MFU} \times F}.
$$

For Qwen3-8B ($n_\text{layers}=36$, $d_\text{hidden}=4{,}096$), the weight term is 16B FLOPs/token and the attention term adds 2.4B at a 4K prompt:

$$
C_\text{in} = 2 \times 8\text{B} + 4 \times 36 \times 4{,}096 \times 4{,}000 \approx 18.4\text{ B FLOPs/token}.
$$

$$
G_\text{prefill} = \frac{2 \times 4{,}000 \times 18.4\text{B}}{0.5 \times 990\text{T}} \approx 0.30.
$$

Below $L_\text{in} \approx 6\,d_\text{hidden}$ the weight term dominates and $C_\text{in} \approx 2P_a$; above it, attention takes over and total prefill compute scales as $L_\text{in}^2$. That crossover is roughly 6K tokens for a 0.6B model, up to 50K for 72B.

::content-collapsible{title="Where the per-token cost comes from"}
**The weight cost.** A forward pass multiplies the token against every active weight in the model, and each weight is one multiply and one add: 2 FLOPs. So $P_a$ active parameters cost $2P_a$ per token. A dense model hits all of them ($P_a = P$); an MoE routes each token through only a few experts, so $P_a \ll P$ and prefill is proportionally cheaper.

**The attention cost.** Attention is $\text{softmax}(QK^\top / \sqrt{d_\text{head}})V$. Q, K, and V come from weight projections, already counted above in $2P_a$. The $QK^\top$ term scores each token's query against every token's key. With $L_\text{in}$ tokens, that is $L_\text{in}^2$ score pairs. Each score is a dot product over $d_\text{head}$ dimensions, so per head $QK^\top$ costs $2\,d_\text{head}\,L_\text{in}^2$ FLOPs. The $\times V$ term then uses those scores as weights to mix the value vectors. It has the same shape, so it costs the same. That is $4\,d_\text{head}\,L_\text{in}^2$ per head.

Summing across heads uses $n_\text{heads} \cdot d_\text{head} = d_\text{hidden}$, collapsing the per-head $d_\text{head}$ into a single $d_\text{hidden}$. GQA shrinks the key and value side, but it keeps every query head, so the full $d_\text{hidden}$ still applies. Across all layers, the per-token cost is $4\,n_\text{layers}\,d_\text{hidden}\,L_\text{in}$.

**The crossover.** A standard layer has roughly $12\,d_\text{hidden}^2$ parameters; the FFN dominates :content-cite{n="7"}. So $2P_a \approx 24\,n_\text{layers}\,d_\text{hidden}^2$. Setting the weight cost equal to the attention cost gives $L_\text{in} \approx 6\,d_\text{hidden}$: depth cancels, and the crossover is just six times the model's width. Above that, the attention term dominates the per-token prefill FLOPs.
::

<aside class="border-border text-muted-foreground my-6 border-l-2 pl-4">
  <strong class="text-foreground font-medium">Takeaway:</strong>
  Prefill is a compute bill. Long prompts and dense active parameters move this term.
</aside>

## Step 2b: Decode Is a Bandwidth Bill

Decode writes the answer one token at a time. Each output token depends on the one before it, so a single request cannot be parallelised across time. Serving systems recover parallelism by batching requests instead, so one decode step advances $B$ active streams by one token.

Each decode step streams bytes from HBM. It reads the weights once across the batch, and it reads the KV cache once per stream. The arithmetic is small compared to this traffic, so decode is usually bandwidth-bound :content-cite{n="10"}.

A single GPU has usable bandwidth $\text{MBU}\cdot\text{BW}$, where MBU is model-bandwidth utilization. We use MBU $\approx 0.6$ :content-cite{n="9"}. But the latency target has first claim on that bandwidth: to produce one token every $t$ seconds, the card has to read $W$ bytes of weights, consuming $W/t$ bandwidth. Subtract that fixed weight read from usable bandwidth to get what remains for KV traffic:

$$
\text{MBU}\cdot\text{BW} - W/t.
$$

With request rate $R$, output length $L_\text{out}$, average context $\bar n = L_\text{in} + L_\text{out}/2$, and per-token cache $M_\text{kv/tok}$, the decode bill is:

$$
G_\text{decode} = \frac{R \times L_\text{out} \times \bar n\, M_\text{kv/tok}}{\text{MBU}\cdot\text{BW} - W/t}.
$$

For Qwen3-8B, $W=16\text{ GB}$ and $\bar n=4{,}500$. On an H200, usable bandwidth is $0.6 \times 4.8\text{ TB/s}$, and the weight read consumes $16\text{ GB}/50\text{ ms}$:

$$
G_\text{decode} = \frac{2 \times 1{,}000 \times 4{,}500 \times 144\text{ KB}}{0.6 \times 4.8\text{ TB/s} - 16\text{ GB}/50\text{ ms}} \approx 0.52.
$$

If $W/t$ approaches $\text{MBU}\cdot\text{BW}$, the GPU cuont explodes. We cannot hit the TPOT target without splitting the model across GPUs to shrink the per-GPU weight read (and each split adding all-reduce network overhead per step).

::content-collapsible{title="Where the decode GPU count comes from"}
Each decode step reads the weights once across the batch ($W$ bytes) and the KV history once per stream. With $B$ streams, average context $\bar n$, and effective bandwidth $\text{MBU}\cdot\text{BW}$, the step time is:

$$
t_\text{step} = \frac{W + B\,\bar n\, M_\text{kv/tok}}{\text{MBU}\cdot\text{BW}}.
$$

Require $t_\text{step} \le t$ and solve for $B$. The step's byte budget is $\text{MBU}\cdot\text{BW}\cdot t$; subtract the fixed weight read $W$ and divide by the per-stream KV cost:

$$
B \le \frac{\text{MBU}\cdot\text{BW}\cdot t - W}{\bar n\, M_\text{kv/tok}}.
$$

One decode step advances all $B$ streams by one token, so the GPU produces $B$ tokens in $t$ seconds. Demand is $R \times L_\text{out}$ tokens per second, so GPU count is $R \times L_\text{out} \times t / B$. Substitute the batch ceiling above and cancel $t$:

$$
G_\text{decode} = \frac{R \times L_\text{out} \times \bar n\, M_\text{kv/tok}}{\text{MBU}\cdot\text{BW} - W/t}.
$$
::

MoE models trip people up here. A 30B-A3B serves like a 3B model in prefill because only 3B parameters activate per token. Decode does not get the same discount. It is bandwidth-bound: what matters is bytes streamed from HBM per step, not FLOPs. All experts have to live in memory, and under load different requests pull different expert subsets simultaneously. By the time the batch is served, nearly the full pool has been read.

<aside class="border-border text-muted-foreground my-6 border-l-2 pl-4">
  <strong class="text-foreground font-medium">Takeaway:</strong>
  Decode is a bandwidth bill. It rises with output tokens and with the average KV cache each token has to read.
</aside>

## Step 3: Combine the Bills

Now take the larger of the memory bill and the throughput bill.

$$
G = \max\big(G_\text{fit},\ G_\text{prefill} + G_\text{decode}\big)
$$

For our example, Qwen3-8B at 2 req/s, 4K input, 1K output, and 50 ms TPOT is a one-card H200 job before operational margin. The three bills collapse to:

$$
G = \max(0.7,\ 0.30 + 0.52) \approx 0.8.
$$

The workload shape determines which compute term leads. Long prompts and short answers, like RAG, coding, multi-turn chat, and agents, push prefill up. Long outputs push $\bar n$ up and shift the cost into decode and the KV cache, as in reasoning models and long-form generation.

## Run the Napkin

If you want to adapt this to your own workload, start here. The script below uses the same formulas as the walkthrough. Change the constants at the top for your model, hardware, and traffic shape; it prints the memory, prefill, decode, and final bills separately, not just the rounded GPU count.

::content-collapsible{title="Show the script"}
```python
import math

# -----------------------------
# Model
# -----------------------------
TOTAL_PARAM = 8e9      # total resident parameters
ACTIVE_PARAM = 8e9     # active parameters per token
PRECISION = "bf16"     # bf16 = 2 bytes, fp8 = 1 byte

# Standard-GQA KV cache details.
# For hybrid/MLA/etc., set KV_PER_TOKEN_BYTES directly.
NUM_LAYERS = 36
NUM_KV_HEADS = 8
HEAD_DIM = 128
KV_PER_TOKEN_BYTES = None  # Default: 2 * layers * kv_heads * head_dim * bytes

# Prefill attention term.
D_HIDDEN = 4096

# -----------------------------
# Traffic
# -----------------------------
REQ_RATE = 2         # requests / second
CTX_IN = 4_000       # input tokens / request
CTX_OUT = 1_000      # output tokens / request
TPOT_S = 0.050       # time per output token target, in seconds

# -----------------------------
# Hardware and utilization
# -----------------------------
ACCELERATOR = "h200"
MFU = 0.5            # model FLOPs util during prefill
MBU = 0.6            # model bandwidth util during decode
OVERHEAD = 1.15      # CUDA context, fragmentation, etc.

PRECISION_BYTES = {
    "bf16": 2,
    "fp8": 1,
}

ACCELERATORS = {
    "h200": {
        "mem_bytes": 141e9,
        "bw_bytes_s": 4.8e12,
        "flops_s": 990e12,  # dense bf16 FLOPs, not sparsity-assisted peak
    },
}

b = PRECISION_BYTES[PRECISION]
hw = ACCELERATORS[ACCELERATOR]

weights_bytes = TOTAL_PARAM * b
kv_per_token_bytes = (
    KV_PER_TOKEN_BYTES
    if KV_PER_TOKEN_BYTES is not None
    else 2 * NUM_LAYERS * NUM_KV_HEADS * HEAD_DIM * b
)

avg_seq_len = CTX_IN + CTX_OUT / 2
request_latency_s = CTX_OUT * TPOT_S
concurrency = REQ_RATE * request_latency_s

kv_bytes = kv_per_token_bytes * avg_seq_len * concurrency
g_fit = (weights_bytes + kv_bytes) * OVERHEAD / hw["mem_bytes"]

c_in = 2 * ACTIVE_PARAM + 4 * NUM_LAYERS * D_HIDDEN * CTX_IN
g_prefill = REQ_RATE * CTX_IN * c_in / (MFU * hw["flops_s"])

usable_bw = MBU * hw["bw_bytes_s"]
weight_bw = weights_bytes / TPOT_S
remaining_bw = usable_bw - weight_bw
if remaining_bw <= 0:
    raise ValueError(
        "One GPU cannot meet this TPOT; "
        "split the model or relax TPOT."
    )

g_decode = REQ_RATE * CTX_OUT * avg_seq_len * kv_per_token_bytes / remaining_bw

g_throughput = g_prefill + g_decode
g_final = max(g_fit, g_throughput)


def gb(x):
    return x / 1e9


def kb(x):
    return x / 1e3


print("=== Inputs ===")
print(f"accelerator: {ACCELERATOR}, precision: {PRECISION}")
print(
    f"rate: {REQ_RATE:g} req/s, input: {CTX_IN:,} tok, "
    f"output: {CTX_OUT:,} tok, TPOT: {TPOT_S*1000:.0f} ms"
)
print()

print("=== Memory ===")
print(f"weights: {gb(weights_bytes):.1f} GB")
print(f"KV/token: {kb(kv_per_token_bytes):.0f} KB")
print(f"avg sequence length: {avg_seq_len:,.0f} tokens")
print(f"concurrency: {concurrency:,.0f} requests")
print(f"resident KV cache: {gb(kv_bytes):.1f} GB")
print(f"G_fit: {g_fit:.2f}")
print()

print("=== Prefill ===")
print(f"C_in: {c_in/1e9:.1f}B FLOPs/token")
print(f"G_prefill: {g_prefill:.2f}")
print()

print("=== Decode ===")
print(f"usable bandwidth: {gb(usable_bw):.0f} GB/s")
print(f"weight bandwidth at TPOT: {gb(weight_bw):.0f} GB/s")
print(f"bandwidth left for KV: {gb(remaining_bw):.0f} GB/s")
print(f"G_decode: {g_decode:.2f}")
print()

print("=== Final ===")
print(f"throughput bill: {g_prefill:.2f} + {g_decode:.2f} = {g_throughput:.2f}")
print(f"final bill: max({g_fit:.2f}, {g_throughput:.2f}) = {g_final:.2f}")
print(f"rounded GPUs: {math.ceil(g_final)}")
```
::

## Turning the Knobs

We demonstrated the mechanics through the working example. Now we change one input at a time and watch which bill moves. Each case below is one constant changed at the top of the script.

**Raise the rate.** Keep the dense 8B and the 4K-in, 1K-out shape, but push demand from 2 to 20 requests/sec. The load-dependent terms scale almost linearly: prefill grows to about 3 H200s, decode to about 5, and the KV-heavy fit floor to about 6.

$$
G \approx \max(6,\ 3 + 5) \approx 8.
$$

**Change the shape.** Back to 2 requests/sec on the dense 8B, but vary the request shape. With 16K-token prompts and 1K-token answers, prefill rises because the prompt is longer, and decode rises because the average context is now 16.5K tokens. The bills are about 2 H200s for fit, 1.6 for prefill, and 1.9 for decode, so the answer is roughly four cards.

With 8K-token prompts and 8K-token answers, prefill is still under one H200, but decode jumps to about 11. Every one of the 8,000 output tokens rereads a cache averaging 12K tokens. The resident KV cache also grows to roughly the same size, so the answer is about 12 cards, with decode and KV cache as the binding terms.

**Swap the model.** Return to the original 2 requests/sec, 4K-in, 1K-out workload, but trade the dense 8B for Qwen3-30B-A3B. The MoE moves two numbers in opposite directions.

For prefill, 4K tokens sit well below the attention crossover for this model, so $C_\text{in} \approx 2 \times P_a = 6\text{B}$:

$$
G_\text{prefill} \approx \frac{2 \times 4{,}000 \times 6\text{B}}{0.5 \times 990\text{T}} \approx 0.1.
$$

Decode does not get that discount. Under load the batch touches nearly the full expert pool, so the weight-read term uses all 60 GB:

$$
G_\text{decode} = \frac{2 \times 1{,}000 \times 4{,}500 \times 144\text{ KB}}{0.6 \times 4.8\text{ TB/s} - 60\text{ GB}/50\text{ ms}} \approx 0.8.
$$

The MoE buys cheap prefill, not a cheap decode budget. That pays off most for multi-turn chat, where each turn re-sends the full transcript: $L_\text{in}$ climbs with the conversation while $L_\text{out}$ per turn stays short.

::content-collapsible{title="Why do labs still pick MoE?"}
Training is the first reason labs still pick MoE. A 30B-A3B costs roughly 3B-equivalent compute to train but can deliver quality closer to a dense 30B. The training costs usually dwarfs the serving bill.

The workload often fits MoE too. Frontier labs today focus on coding agents which use large code contexts and short tool responses. That shape is prefill-heavy, not decode-heavy, so MoE's cheap prefill is the right trade.

Prefix caching also shifts the decode picture. An agentic loop accumulates context each turn, but the serving engine caches the growing prefix and only prefills the incremental append. Re-reading all 60 GB of weights per decode step remains expensive, but the KV traffic that dominates the decode term is partly absorbed by the cache.
::

The cases line up like this; the bottleneck changes with traffic shape:

| Model | RPS | In / Out | $G_\text{fit}$ | $G_\text{prefill}$ | $G_\text{decode}$ | Answer | Bottleneck |
|:--:|---:|---:|---:|---:|---:|---:|:--:|
| 8B | 2 | 4K / 1K | ~0.7 | ~0.3 | ~0.5 | 1 | rounds up to 1 |
| 8B | 20 | 4K / 1K | ~6 | ~3 | ~5 | ~8 | decode throughput |
| 8B | 2 | 16K / 1K | ~2 | ~1.6 | ~1.9 | ~4 | prefill (long input) |
| 8B | 2 | 8K / 8K | ~11 | ~0.7 | ~11 | ~12 | KV + decode (long output) |
| 30B-A3B | 2 | 4K / 1K | ~1 | ~0.1 | ~0.8 | ~1 | weights (MoE) |

  <strong class="text-foreground font-medium">Takeaway:</strong>
  The same model can be memory-bound, prefill-bound, or decode-bound depending more on traffic shape than on parameter count alone.
</aside>

## A Floor, Not a Target

You now have an answer to both questions: the weights and KV cache fit on $G_\text{fit}$ cards; throughput demands at least $G_\text{prefill}$ plus $G_\text{decode}$ cards. Treat that result as a floor, not a target.

Real deployments usually land 20 to 30 percent higher. MFU sags under load, prefill and decode compete for bandwidth on shared cards, and tensor parallelism eats into both. The napkin gets the order of magnitude and names the bottleneck; a benchmark against your actual traffic tightens the number before you commit hardware.
